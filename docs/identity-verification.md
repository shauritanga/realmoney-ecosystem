# Document and live-selfie verification (policy 2)

## Delivery status

The app and backend implement hosted capture session orchestration and strict result
validation. **No live document/liveness vendor adapter is included or provisioned.**
The configured private `VERIFICATION_BRIDGE_URL` must implement the contract below
using a real approved provider before this feature can be enabled. Front/back photo
capture, image-quality validation, document authentication, spoof detection, face
matching and manual review run in that provider's hosted flow. The app does not
implement a homegrown liveness detector or store ID images in its gallery/cache.
No synthetic result is automatically generated by the new session flow.

Do not deploy this as an operational KYC system until a real provider has passed
end-to-end acceptance tests, including supported Tanzanian document versions. It
is an identity-verification component, not a complete AML/compliance programme.

## User flow

1. Registration selects NIDA, voter ID, driving licence or passport.
2. Verification shows front/back instructions for cards, biodata page for passports,
   and live selfie instructions. It displays the operator-approved biometric notice
   and requires explicit acceptance of its exact version before starting capture.
3. Backend creates or resumes a borrower-bound session. The app launches only its
   returned HTTPS URL in the external browser. Camera permissions belong to the
   hosted flow. Provider UI must permit retakes and handle denied camera access,
   interrupted uploads, glare, blur and poor connectivity.
4. On return the app refreshes through its authenticated backend. The borrower may
   also press Check verification status. A browser redirect is never approval.
5. Processing and review do not unlock financial/wallet submission or borrowing.
   Eligibility is checked again at loan approval and before payout.
   Review happens in the provider's access-controlled console. The admin borrower
   review exposes the provider reference and a refresh action, not an override.
6. Rejected/expired captures can restart, limited to three successfully created
   sessions in 24 hours. Refreshes are limited to one provider call per 15 seconds
   per account. Verified sessions are terminal; identity changes invalidate them.

## Backend API

All borrower routes require JWT + BORROWER role; subject IDs come from the token.

- `GET /api/v1/onboarding`: includes `identityVerification` public summary, required
  sides, status, current notice/version and availability. Never includes capture URL,
  session internals, raw biometric images or full provider payload.
- `POST /api/v1/onboarding/identity/session` with `{consent:true, noticeVersion}`:
  creates/resumes capture and returns the public summary and `hostedUrl` (or null
  when processing/review/verified). Treat the URL as a short-lived bearer secret.
- `POST /api/v1/onboarding/identity/refresh`: fetches provider evidence server-side.
  Client-supplied results, identifiers or verification flags are not read.
- Legacy `POST /api/v1/onboarding/verify-identity` rejects requests with an update
  instruction. Existing apps must upgrade.
- `POST /api/v1/admin/borrowers/:id/identity/refresh`: ADMIN-only provider refresh.

Identity readiness requires policy 2, matching current identity fingerprint, passed
required checks, accepted mode and verified status. Old identity approvals need a
new verification. Legacy `auto-wallet-*` approvals need a real wallet lookup.
`AUTO_VERIFY_*` flags no longer grant live approvals.

## Private provider bridge contract

Every request uses `Authorization: Bearer VERIFICATION_BRIDGE_TOKEN`, HTTPS, a
10-second timeout and no redirects. Keep the bridge private, authenticated and
rate-limited. It must not log documents, selfies, secrets or hosted session URLs.

### POST /identity/sessions

Request:

```json
{
  "requestId": "opaque idempotency key",
  "subjectId": "borrower UUID",
  "policyVersion": 2,
  "identity": {
    "type": "NIDA",
    "fullName": "Synthetic Borrower",
    "number": "19900101123450000101",
    "dateOfBirth": "1990-01-01"
  },
  "requiredSides": ["front", "back"],
  "requiredChecks": ["documentAuthenticity", "registrationMatch", "liveness", "faceMatch"],
  "consent": {"version": "sha256 of approved text", "text": "approved notice", "acceptedAt": "ISO timestamp"}
}
```

Create a session whose document type and required checks cannot be changed by the
browser. Enforce original-document capture and anti-injection controls appropriate
to the provider. The provider may reject unsupported document versions; it must
never silently substitute a weaker flow. Use `requiredSides:["biodata"]` for passports.

Response:

```json
{
  "sessionId": "provider-session-id",
  "requestId": "same request key",
  "subjectId": "same borrower UUID",
  "mode": "live",
  "hostedUrl": "https://approved-capture-host/session-token",
  "expiresAt": "future ISO timestamp, at most 24 hours away"
}
```

Session IDs allow 1–200 ASCII letters, numbers, underscores and hyphens. Capture
hosts must exactly match `IDENTITY_CAPTURE_HOSTS`; no credentials or nonstandard
port in URLs. The adapter must keep the borrower/request mapping server-side and
return it from authenticated records, not browser query parameters.

### GET /identity/sessions/:sessionId

Fetch latest authenticated vendor evidence, including any reviewed result. If using
vendor webhooks inside the adapter, verify signatures, timestamp/replay protection,
state ordering and session binding before updating its records. Our application
uses authenticated polling, so it exposes no public result webhook to spoof.

```json
{
  "sessionId": "provider-session-id",
  "requestId": "same request key",
  "subjectId": "same borrower UUID",
  "mode": "live",
  "status": "verified",
  "document": {
    "authentic": true,
    "capturedSides": ["front", "back"],
    "type": "NIDA",
    "fullName": "Synthetic Borrower",
    "number": "19900101123450000101",
    "dateOfBirth": "1990-01-01"
  },
  "liveness": {"passed": true},
  "faceMatch": {"passed": true}
}
```

Statuses: `capture_required`, `processing`, `review`, `verified`, `rejected`,
`expired`. Only `verified` can grant approval, and only if every required check
passes. Missing/failed checks downgrade even an overall approval to `review`.
Document attributes are read from provider evidence, not copied from the request.
Names match with Unicode normalization, case and whitespace normalization; identity
numbers ignore spaces/hyphens. Other differences require investigation; no fuzzy
match auto-approval. Correct registration data through the existing verified-phone
flow before recapture if necessary.

`development` results are accepted only with non-production `NODE_ENV` and explicit
`ONBOARDING_DEV_MODE=true`; label them visibly and use synthetic data only.

## Operations and deployment

1. Select/contract the provider, confirm document coverage, liveness/PAD testing,
   face-match performance, manual-review handling, accessibility fallback and data
   processing/transfer terms. The adapter must keep all three checks mandatory.
2. Implement and test this bridge contract against its sandbox. Configure server-side
   credentials, exact capture hosts and an approved notice. Do not put credentials
   into Flutter build arguments. Keep `IDENTITY_VERIFICATION_ENABLED=false` until ready.
3. Define provider retention/deletion and access policies; encrypt provider storage,
   restrict staff access, audit reviews, and arrange incident handling. Deleting local
   account records does not delete vendor-held evidence: implement the vendor deletion
   operation alongside the account-deletion service (currently unavailable).
4. Deploy backend and app together. JSONB onboarding stores policy/session metadata;
   no new SQL column is needed. Back up the database and account for existing users
   needing recapture. Do not restore auto-verify flags as a compatibility workaround.
5. Run real sandbox acceptance: all supported IDs, missing back, wrong document,
   wrong person, static photo/replay, expired document, denial/review, bad network,
   session timeout, camera denial, app resume and successful complete loan eligibility.
6. Then enable and monitor. This repository does not provision or deploy the bridge,
   approve notices, select retention periods or activate a production account.
